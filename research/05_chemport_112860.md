## 3. Parallel execution

### 3.1 RI methods hang when a process gets no work ("idle nodes")
- **EvgeniX (2015-06-22), bug report.** In a parallel RI-MP2 run the output prints integral blocks per node,
  for example:
  ```
   time: integral estimates               :     6.1  [     0.8     0.8     0.8     0.8     0.8     0.8     0.8     0.8 ]  99.9%     0.8
       2892490 blocks,    103625770 integrals on node  0
       3681560 blocks,     91256706 integrals on node  1
       3384450 blocks,     99587430 integrals on node  2
       3284560 blocks,     94073242 integrals on node  3
       3050281 blocks,     86236315 integrals on node  4
       3839829 blocks,    104329957 integrals on node  5
       3357365 blocks,     80347849 integrals on node  6
       3755357 blocks,     94130627 integrals on node  7
      27245892 blocks,    753587896 integrals total
  ```
  If **any process gets 0 blocks** (the job is too small for that many processes), "задача беспросветно зависает"
  (the job hangs indefinitely, with no error). His guess: "не хватает проверок для 'холостых' узлов" (the code
  lacks checks for idle nodes).
- **amge (2015-06-23) confirms:** "RI-методы (и ridft тоже) почему-то не терпят холостых узлов. Это, конечно, бага,
  но бороться легко: пускать маленькие задачки на одном ядре." In English: RI methods, **including RI-DFT**,
  do not tolerate idle nodes. It is a bug. Workaround: **run small jobs on one core** (or fewer processes).
- Manual tip: for RI-MP2 or RI-DFT on small molecules, use few MPI processes. If a parallel job hangs right after
  `integral estimates`, look for a `0 blocks ... on node N` line.

### 3.2 Reading the timing lines
`time: <step> : <total> [ <per-node times> ] <efficiency%> <wall/max>`. Example from the same run:
`time: Inversion of V-Matrix : 0.6 [ 0.6 0.0 0.0 0.0 ] 25.0% 0.6`. Here the V-matrix inversion runs on node 0
only, so parallel efficiency is 25% on 4 processes. (This is an interpretation of the format; nobody in the thread
explains it.)

## 4. Memory / disk

### 4.1 `$system` syntax seen in the thread
```
$system memory=512 disk=-1024 path=/tmp $end
$system memory=2048 disk=50 path=/tmp $end
$system mem=1800 disk=-3000
$end
```
- `mem=` is accepted as a short form of `memory=` (YuraM). Values are in MB.
- A **negative `disk`** value is used by experienced users. With `memory=512 disk=-1024` the program printed
  `Memory: 512m + 1024m (512m + 1024m)`, so the absolute value of `disk` appears as a second memory amount. The
  exact meaning of the sign is not explained in the thread. Cross-check it with the official docs.

### 4.2 RI-MP2: small job reports it "does not fit in memory" unless `direct=1`
- **EvgeniX (2015-06-22), reproducible case.** A tiny molecule (CH3NH2 with an extra H, 7 atoms) in `basis4.in`
  with RI-MP2 and `four=1` fails, saying the job does not fit in memory. Larger jobs run fine. Input as posted:
  ```
  $system memory=2048 disk=50 path=/tmp $end
  $control theory=RIMP2 four=1 basis="basis4.in" task=energy $end
  $grid acc=1e-9 $end
  $scf restrict=0 conv=1e-10 $end

  $molecule charge=0 mult=1 cartesian
   set=L22
     6   0.00019820  -0.27105963  -0.49946877
     1  -0.49673873  -1.25135803  -0.51592016
     1  -0.39133522   0.29616255  -1.35571802
     7  -0.34535244   0.42674023   0.74301809
     1   0.12520784   1.33341575   0.76638407
     1   0.02808578  -0.09223403   1.54003954
     1   1.07993460  -0.44166690  -0.67833465
  $end
  ```
  **Workaround:** add
  ```
  $integral direct=1 $end
  ```
- EvgeniX (follow-up, 2015-06-23): the same job runs with a smaller basis set and also with a bigger one. Only this
  set (`set=L22` in `basis4.in`) fails, "сколько памяти не укажи (без direct=1)" (however much memory you give,
  unless `direct=1` is set). Changing the number of processes does not help.
- amge (2015-06-23) reproduced it. In his run it crashes with the cryptic message:
  ```
  0: write VMNN(11753704:14042536)?
  ```
  Treat it as a bug in the non-direct RI-MP2 path for some basis and size combinations. **Workaround: `$integral direct=1 $end`.**

Observations taken from the output:
- `$scf` has **two-valued** `convergence` and `iterations`. The output line
  `scf options: conv=1.0e-10, 1.0e-03; iter=999,999` shows that a single value sets only the first; the second
  defaulted to `1.0e-03`.
- With CCSD (HF reference) and no `iterations` given, the output shows `iter=48,16`, which are probably the
  defaults for that theory. The divergent run stops at iteration 47 (48 iterations, numbered 0 to 47).
- The `$grid` line `grid: accuracy=1.0e-12,1.0e-05, cut=1.0e-14,1.0e-07, t=0` shows that `accuracy` has a second
  component (default `1.0e-05`). The cutoffs are derived from it.
- `cut-off for S,T,V integrals: 1.0e-10 (1.0e-06)`. It follows the SCF convergence (1.0e-08 in the CCSD run).
- Keywords are case-insensitive (`OLYP` and `pbe`). Keywords can span several lines inside a group (YuraM's input
  puts one keyword per line, with blank lines between them).
- Molecule block: `$molecule charge=+1 mult=2 cartesian` followed by `set=L2` on the next line, then one line per
  atom (`Z x y z`) in Angstrom. Charge may be written as `+1`.

### 5.1 `$scf` parser quirk: `iterations` vs `convergence` (error `unknown name erations`)
- **EvgeniX (2015-06-22):** in
  ```
  $scf restrict=0 procedure=BFGS iterations=999,999 convergence=1e-10 $end
  ```
  if `convergence` comes **before** `iterations`, "из-за числа '1e-10' секция входного файла не будет прочитана до
  конца и расчёт не пойдёт". In English: because of the number `1e-10`, the rest of the section is not read and
  the job does not start. With `iterations` first, it works (his output shows both values were accepted).
- **amge (2015-06-23):** for him the two words do not work together **in either order**:
  ```
  *** error in '$scf' : unknown name erations
  ```
- EvgeniX: he also tried abbreviations (`conv`, `convergence`, and others) and saw the same problem.
- The error message `unknown name erations` suggests that the leading `it` of `iterations` gets swallowed after a
  number in exponent notation, or that `it` is consumed as a separate prefix token. This is speculation; no
  official explanation is given.
- **Practical advice for the manual:** if you get `unknown name erations`, put `iterations` before
  `convergence`, put them on separate lines, or write the threshold without exponent notation. Then check the
  `scf options:` line in the output to confirm both values were read. Note that YuraM's 2016 input uses
  `convergence=1e-6,1e-3` and `iterations=150,150` on separate lines, convergence first, and does not report a parse
  error.

## 6. Basis sets and basis files

- `basis="basis.in"` (non-relativistic library) is used with `set=L1`, `set=L2`.
  `basis4.in` (with `four=1`) is used with `set=L22`, `set=L3`.
- For DFT the output prints **two** "Basis set input" blocks: the orbital basis and the auxiliary (density-fitting)
  basis. In the summary box these appear as `Dimension of wavefunction basis 506` and
  `Dimension of   auxiliary  basis   1127`. Format: `<n> <Z> <El> : <contracted>/<primitive> : {per-l contracted}/{per-l primitive}`, for example
  ```
      1  29 Cu :  84/234 : {8,7,5,3,1}/{23,18,13,8,4}       (orbital, L2)
      1  29 Cu : 305/598 : {15,14,13,9,7,4,1}/{23,22,20,17,14,9,5}   (auxiliary)
  ```
- Frozen-core info is printed before the basis blocks, for example `atom 29 core =  2,  1,  0`,
  `atom 6 core = 1, 0`, `at.d.=0`. The summary shows `Number of core electrons 13` for the Cu complex.

## 7. SCF convergence problems & fixes

  ```
  $end
  ```
  (Cu(II) with two methylamine ligands and acetate, cation, doublet.)
- **What happens (key output):** the SCF first runs on a **coarse grid** (`Grid: 33008 points`) and converges to
  about 1e-5 gradient by iteration 31 (E = -2061.0592051115). Then it **switches to the fine grid**
  (`Grid: 1084484 points`) and, after about 30 iterations of slow oscillation, blows up:
  ```
   Grid:  1084484 points
    32  -2061.0584149064   0.0007902051   0.01021068    421.8
  ...
    61  -2061.0589819854  -0.0001609359   0.00706632   1471.9
    62  -2060.9713081289   0.0876738565   0.08316847   1508.0
  ...
   102     25.4566988072 892.4250366580  30.63445523   2956.6
   103     29.0486339432   3.5919351360  43.82300487   2992.8
  ```
  "Полная энергия доходит до +29 Хартри!" (the total energy reaches +29 hartree). The run never recovers and
  wanders between -100 and -2000 Eh until it is killed (iteration 196 shown). The same happens with BLYP.
  - Takeaway: PRIRODA's SCF uses a two-stage grid (coarse, then fine). Divergence can start **at the grid
    switch**. A gradient spike at that point is normal, sustained growth is not.
- **Fix 1, amge (2015-06-23):** "Побороть в этом случае можно" by running
  ```
  task=optimize+hessian
  $scf restrict=0 convergence=1e-10 $end
  ```
  In other words, drop `procedure=BFGS` and `iterations`, and do an optimization before the Hessian so that each
  step starts from the previous wavefunction.
- **Fix 2, EvgeniX (2015-06-23):** he solved it by **saving the wavefunction at the very beginning of the
  optimization and loading it** for the Hessian job. For an already-optimized structure, the from-scratch initial
  guess turned out to be poor ("для уже оптимизированного соединения приближение волн.функции изначально плохое
  получается"). He calls this essentially the same solution as amge's. Relevant keywords (syntax from YuraM's
  input): `$control save=<name>.chk $end` to write it, `$guess read=1 $end` to read it.
- Manual tip: for hard open-shell transition-metal cases, (1) get a converged wavefunction from an earlier job,
  save it, and restart from it with `$guess read=1`; (2) or chain `task=optimize+hessian`; (3) `procedure=BFGS`
  is not a cure-all and may itself be involved in this failure.

## 15. Correlated methods (RI-MP2, CCSD)

- `theory=RIMP2` and `theory=CCSD` exist and are run with `task=energy`.
- RI-MP2 known problems: hangs when a process has no work (§3.1); "does not fit in memory" or
  `0: write VMNN(...)?` for some small jobs unless `$integral direct=1 $end` (§4.2).
- CCSD: the HF reference SCF can diverge (§7.2). For CCSD the summary box shows no auxiliary basis.

## 16. Output parsing / visualization

Formats seen in the thread that a parser should handle:
- Header: `date: ...`, `parallel on N processors`, `node i: 'host'`, `Memory: <m>m + <d>m (...)`.
- `molecule input: ''`, `22 atoms, 95 electrons`, the coordinate echo ending with ` #`, `formula: H13C4N2O2Cu`,
  the `internuclear distances:` table (`Cu1 | O2 : 1.98675 N1 : 2.01070 ...`), `largest = 7.39886`.
- Summary box between `+-----` lines: `Number of atoms`, `Charge of molecule`, `Spin multiplicity`,
  `Number of alpha electrons`, `Number of beta  electrons`, `Number of core  electrons`, `Theoretical Method`,
  `Approximation to E(xc)`, `Dimension of wavefunction basis`, `Dimension of   auxiliary  basis`,
  `Hamiltonian: non-relativistic`.
- DFT SCF table: `it. energy energy change gradient time`, with `Grid: N points` lines inserted when the grid
  changes. HF table: `it. energy change gradient change time integrals`.
- Fixed-width numbers can run together when large, for example `109   -276.00212718591046.8992613495  19.71998501`.
  **Parse by column position, not by whitespace.**
